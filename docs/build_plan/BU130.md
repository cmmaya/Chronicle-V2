# BU130 — Google Account Sign-In (OAuth Desktop Flow)

Status:
Completed

Goal:
Let the user connect a Google account to Chronicle with a normal "Sign in with
Google" page in their browser. Keep the resulting credentials in the Windows
Credential Manager, so later BUs can call the Google Calendar API for that
user.

Context:
- Chronicle is an installed Windows app (BU126/BU127). Google's supported
  sign-in flow for a desktop app is OAuth 2.0 with a **loopback redirect**: the
  app opens the system browser and listens on `http://127.0.0.1:<random
  port>`. Google redirects there with an authorization code, and the app
  exchanges the code for tokens. PKCE (`S256`) protects that exchange.
- The flow needs an OAuth client (a client ID and a "secret" that Google treats
  as non-confidential for desktop apps). The user chose to support **both**
  options:
  - **Chronicle client** (default): shipped with the app. Until the Google
    Cloud project passes Google's verification, users see the "Google hasn't
    verified this app" screen, and only accounts listed as test users (at most
    100) can sign in.
  - **Custom client**: the user imports their own `client_secret.json`
    ("Desktop app" type) from their own Google Cloud project.
- BU122 set the rule for secrets: they go to the credential store through
  `keyring` (service `Chronicle`), never to a plain file, and never to the log.
  The refresh token follows the same rule.
- `requests` is already a pinned dependency. The BU120 audit kept the
  dependency list small, so the flow uses `requests` and the standard library
  (`http.server`, `secrets`, `hashlib`, `webbrowser`) instead of pulling in
  `google-auth-oauthlib` / `google-api-python-client`.

Decisions:
- Scopes: `openid email` (to show which account is connected) and
  `https://www.googleapis.com/auth/calendar.events`, the narrowest scope that
  can create events on the user's own calendars. The code must not request the
  full `calendar` scope.
- Credential storage:
  - Refresh token in keyring, user `google_calendar_refresh_token`.
  - Access token in memory only. It is refreshed when it expires or on a 401.
  - Connected email and client source (`chronicle` / `custom`) in
    `preferences.json`. Neither is a secret.
  - The custom client JSON is copied to `paths.data_dir() / "google_client.json"`.
- The bundled Chronicle client is read from
  `paths.resource_dir() / "google_oauth_client.json"`. That file is
  git-ignored and added at build time (packaging). In development, the env vars
  `CHRONICLE_GOOGLE_CLIENT_ID` / `CHRONICLE_GOOGLE_CLIENT_SECRET` provide it.
  If neither exists, the Chronicle option is shown as unavailable.

Tasks:
- `src/calendar_sync/google_auth.py`:
  - `load_client(source) -> OAuthClient | None` for `chronicle` or `custom`.
    It validates that the JSON has an `installed` block with `client_id`,
    `client_secret`, `auth_uri` and `token_uri`. A "web" client, or a missing
    field, gives a clear error.
  - `import_custom_client(path)` validates the file and copies it to the data
    dir.
  - `SignInFlow` (runs on a worker thread, not the UI thread):
    1. Bind `127.0.0.1` on port 0, and generate `state` plus a PKCE verifier
       and challenge.
    2. Open the consent URL in the default browser with `access_type=offline`
       and `prompt=consent`, so a refresh token is always returned.
    3. Serve a single request. Reject it if `state` does not match. Handle
       `error=access_denied`. Show a small "You can close this tab and return
       to Chronicle" page.
    4. Exchange the code at `token_uri` and read the email from the `id_token`
       (or from the userinfo endpoint).
    5. Check that the granted scopes include `calendar.events`. If the user
       unticked it on the consent screen, fail with "Calendar permission was
       not granted".
    6. Save the refresh token to keyring. Return the email.
    - It can be cancelled. It times out after 3 minutes and then closes the
      socket.
  - `get_access_token()` refreshes when needed. On `invalid_grant` (revoked
    or expired), it deletes the stored refresh token and raises
    `GoogleAuthExpired`. Callers show "Reconnect your Google account".
  - `disconnect()` makes a best-effort POST to Google's revoke endpoint,
    then always deletes the keyring entry and clears the email.
  - `connection_state() -> (connected: bool, email, source)`.
- `secrets.py`: small helpers to get, set and delete the refresh token under
  the existing `KEYRING_SERVICE`. Extend `redact` so tokens never reach the
  log.
- `.gitignore`: `google_oauth_client.json`, `google_client.json`.
- `docs/setup.md`: the steps to create the Google Cloud project (enable the
  Calendar API, create an OAuth consent screen with the `calendar.events` scope
  and test users, create a "Desktop app" client), and where to put the JSON.

Validation Requirements:

Required:
- executable behavior verified
- no syntax/runtime errors
- Definition of Done satisfied
- manual validation:
  - Sign in with the Chronicle client: the browser opens, consent is given,
    the tab says to return to Chronicle, and the email is stored. The refresh
    token appears in Windows Credential Manager under `Chronicle`.
  - Sign in with an imported custom client works the same way.
  - Cancel on the consent screen: a clean "Sign-in was cancelled" and nothing
    is stored.
  - Untick the Calendar permission: sign-in fails with the permission message,
    and nothing is stored.
  - Revoke access at myaccount.google.com, then call `get_access_token()`:
    it raises `GoogleAuthExpired` and the keyring entry is gone.
  - Grep the log after a full sign-in: no token or client secret appears.

Tests Required:
- yes: `tests/test_bu130.py` (network mocked):
  - `load_client` accepts an `installed` client and rejects `web` clients and
    missing fields
  - the consent URL contains PKCE `S256`, `state`, `access_type=offline` and
    exactly the agreed scopes
  - a callback with the wrong `state` is rejected, and `error=access_denied`
    maps to a cancelled result
  - missing `calendar.events` in the granted scopes fails and stores nothing
  - `invalid_grant` on refresh deletes the refresh token and raises
    `GoogleAuthExpired`
  - `disconnect()` clears local state even when the revoke call fails

Out of Scope:
