# BU144 — Whole Transcript For Specific Session Questions

Status:
Completed

Goal:
A Specific Session question - from the chat or from the detached window's
Live Q&A, live, just stopped, or long finished - is
answered from the session's whole transcript instead of retrieved excerpts,
so the user can ask anything about the current session (broad questions,
"at the end of the class", different wording than the speaker used). Search
stays for All Sessions and for sessions too long to send whole.

Context:
- The FTS search and router were built for All Sessions (BU089), where 19
  sessions cannot fit in one prompt. Specific Session reused the same
  retrieval, which can miss the passage that answers the question (BU141-BU143
  reduced, but did not remove, that risk) and only sends ~12 windows plus a
  ~3000-char recent tail.
- One session fits easily: the largest stored session (77, "Research Methods -
  Article Critique", 2 h 51 min) is ~92k chars, about 23k tokens. The default
  model (`google/gemini-3.8-flash`) accepts far more.
- Cost, OpenRouter prices on 2026-10-09 ($0.75/M input, $3.75/M output,
  $0.075/M cached input), 10-question chat on session 77: current search
  ~$0.06; whole transcript ~$0.21 uncached, ~$0.07 when the prefix cache hits.
- `_build_messages` already puts the per-session constant text in the system
  message so the provider can cache the prefix. A transcript only grows at
  its end, so the cached prefix stays valid while a session records.
- The recorder overlaps consecutive chunks; `live_qa.collapse_overlap` removes
  that duplication and should be applied so the overlap is not paid for twice.
- BU141 already loads every raw row for the session and knows `live` /
  `indexed`; BU142 renders `[HH:MM:SS] (Mic|Sys|Text): text` lines and the
  live / processing note.

Tasks:
- Config: `SESSION["full_transcript_max_chars"]` (default 300000, about
  4-5 hours of speech, ~75k tokens). 0 disables whole-transcript mode.
- Retriever: when the session's transcript (after overlap collapse) is within
  the limit, return it whole - every row, in time order, one
  `[HH:MM:SS] (Mic|Sys|Text): text` line per row, overlap collapsed between
  consecutive rows of the same source - and skip FTS / in-memory search for
  transcripts. Mark the context `transcript_full=True`. Above the limit, keep
  the BU141-BU143 search unchanged.
- Works the same for live, just-stopped and indexed sessions: the rows come
  straight from `transcripts`, so no index is needed and a live question sees
  everything transcribed so far.
- Prompt layout (`_build_messages`), ordered for prefix caching:
  1. agent instruction, then the screenshot contract when screenshots exist
     (moved before the transcript so it is part of the stable prefix);
  2. session header;
  3. `## Full transcript (in time order)` - the whole transcript; while live
     only new lines are appended at the end, so the earlier prefix is reused.
  The summary, the BU142 live / processing note, and the screenshot index move
  to the user message with the question (they change or appear later, so they
  must not sit inside the cached prefix ahead of the transcript).
- When `transcript_full` is set, the per-question evidence has no
  `## Transcripts` excerpt section (no duplicate text); screenshot search still
  runs and still uses the question.
- Detached-window Live Q&A (manual selection and detected questions) gets
  the same whole transcript: it already asks with
  `explicit_scope="current_session"` (`window.py` ~5384), so it goes through
  this path. Its question text embeds up to `LIVE_QA["answer_context_chars"]`
  of earlier transcript under `EARLIER_TRANSCRIPT_PREAMBLE` /
  `CANDIDATE_CONTEXT_PREAMBLE`; in full mode the service removes that block
  with `live_qa.strip_transcript_evidence` before building the prompt, so the
  transcript is not sent twice. The selected excerpt / detected question, the
  answer-mode instruction and the reference document stay as they are. Over
  the limit, the embedded evidence is kept (it is the only recent context the
  search path is guaranteed to have).
- Retrieval (screenshot search, and transcript search over the limit) always
  uses the question without the embedded evidence block, so minutes of
  transcript do not drive the search terms.
- Log, per Specific Session answer, the mode (`full` / `search`) and the
  transcript size in chars, so cost can be checked later.
- Any Session (All Sessions) path is untouched.

Validation Requirements:

Required:
- executable behavior verified
- no syntax/runtime errors
- Definition of Done satisfied
- manual validation:
  - during a recording, ask a broad question ("what has been covered so
    far?") and one about something said 30+ minutes ago - both answered with
    timestamps;
  - during a recording, select an early chunk in the detached window and use
    ANSWER - the answer can draw on anything said before, not only the last
    ~10 minutes;
  - on session 81, ask the original question ("what did she mention about
    the assignment at the end of the class? She gave some advices") - the
    answer cites the 21:12-21:13 advice about the critique / final report;
  - check OpenRouter usage for a second question in the same chat shows
    cached prompt tokens (best-effort; caching is provider-side).

Tests Required:
- yes: `tests/test_bu144.py`
  - a session under the limit returns every row, in time order, overlap
    collapsed, and FTS is not called
  - a session over the limit falls back to the BU141-BU143 search
  - limit 0 disables whole-transcript mode
  - live session in full mode includes rows up to the newest one
  - message layout: system message = instruction (+ screenshot contract) +
    header + full transcript, in that order; summary, note and question are in
    the user message; no `## Transcripts` excerpt section when full
  - appending a row to a live session leaves the system message an exact
    prefix-extension of the previous one (cache-friendly)
  - Any Session prompts unchanged
  - a detached-window question (selection and detected candidate) in full
    mode: evidence block stripped, excerpt / question kept, full transcript in
    the system message; over the limit the evidence block is kept

- Chunking long sessions across several calls
