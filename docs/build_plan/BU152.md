# BU152 — Any Session Context For Unsummarized (Uploaded Audio) Sessions

Status:
Completed

Goal:
All Sessions questions find and use the content of sessions that have no
summary - in practice uploaded-audio sessions - the same way they do for
recorded and text-uploaded sessions.

Context:
- Observed 2026-10-10: "what about the whatsapp audio session?" (follow-up to
  a question about going for coffee) answered "no transcript or summary
  content is provided" for session 84 ("WhatsApp Audio 2026-10-09 at 2.11.13
  PM"), although it has 135 transcript rows, 114 FTS chunks, and the word
  "coffee" in its transcript.
- Cause 1 - no summary: recorded sessions auto-summarize in `finalize_session`
  (`SESSION["auto_summary_after_stop"]`), Upload Transcript chains
  `_summarize_uploaded_session` (BU137), but Upload Audio
  (`window._upload_audio_from_all_sessions` -> `_transcribe_uploaded_session`)
  only transcribes. Session 84 has `summary_status='none'`; 4 sessions in the
  local DB have no summary.
- Cause 2 - empty router profile: `indexer.build_session_profile` uses name +
  date + summary, so an unsummarized session's profile is only its name
  ("WhatsApp Audio ... Keywords: whatsapp, audio"). It routes only when the
  question names it, never on its content.
- Cause 3 - Tier-2 searches the literal question: `build_routed_session_context`
  runs `search_rag_fts(query, session_id=...)`; "whatsapp" / "audio" /
  "session" are not in the transcript, so 0 chunks, and with no summary the
  model got only the `## [S84] ...` header. The earlier coffee question was not
  carried over: BU143's follow-up expansion (`_search_query`) exists only in
  the Specific Session retriever.

Tasks:
- Upload Audio: after `_transcribe_uploaded_session` succeeds with
  transcripts, chain `_summarize_uploaded_session` exactly as Upload
  Transcript does (busy "Summarizing" chip, failure leaves "Needs summary").
  Respect `SESSION["auto_summary_after_stop"]` so the setting governs both
  recorded and uploaded audio.
- Router profile without a summary: `build_session_profile` falls back to the
  transcript - the first ~2000 chars of collapsed transcript text, and keywords
  extracted from the whole transcript (`extract_keywords`) - so content routes
  even before a summary exists. When a summary exists the profile is unchanged.
  Profiles refresh through the existing `index_session_profile` hash check; the
  next summary replaces the fallback.
- Backfill: existing unsummarized sessions get the transcript-based profile
  on the next `index_session_content` / Reindex All. Summaries for them are
  not generated automatically (cost); they stay "Needs summary" in All
  Sessions.
- `FOLLOW_UP_MAX_TERMS` 3 -> 4 (added during implementation): the reported
  follow-up "what about the whatsapp audio session?" has exactly 3 search terms
  and would not have carried the coffee question under the BU143 threshold.
- Any Session follow-ups: the routing query and the Tier-2 chunk query use the
  BU143 follow-up rule - a question with fewer than `FOLLOW_UP_MAX_TERMS`
  search terms is searched together with the previous user question of the
  conversation. Move `_search_query` to a shared helper so both scopes use one
  rule. The persisted question is unchanged.
- Tier-2 fallback: when a routed session returns no chunks for the query and
  has no summary, add its opening chunks (time order, within
  `MAX_CHUNKS_PER_SESSION` and the context budget) so the model sees what the
  session is about instead of a bare header.
