# BU095 — System Audio Capture Supervisor And Watchdog

Status:
Completed

Goal:
Stop the system-audio (loopback) recorder from silently dying mid-session. A long
session must keep capturing system audio for its whole duration even when the
default output device changes underneath it, and the user must be told when a
capture stream is lost and when it comes back.

Context:
Reported symptom: "Session 2026-09-09 20:59 stopped transcribing after an hour or
so, maybe I hit a limit." Diagnosed directly against `sessions/session_046` and a
working copy of `chronicle.db` (never the live file):

- Not a transcription limit — Parakeet is local, no quota. The transcriber
  processed every chunk it was handed.
- The **system-audio capture thread died at 21:41:28**, ~42 minutes into a 2h8m
  session. No system `.wav` chunks exist on disk after that point, so there was
  nothing to transcribe; the DB's system transcripts end at the same timestamp.
  Microphone capture ran the full session (chunks to 23:06, transcripts to
  23:02).
- Same failure in `session_044` (~46 minutes in). Recurring, not a one-off.
- Root cause in `src/audio_capture/system_recorder.py`: `_recording_thread`
  resolved the loopback device once at thread start from `sc.default_speaker()`
  and bound a WASAPI loopback stream to it. When Windows changes the default
  output device — the classic trigger being a Zoom/Meet/Teams call ending, which
  reverts the "communications" device to the "multimedia" default — that stream
  goes stale. The old code then either (a) retried the dead handle forever in the
  inner `except` (log warning, `sleep(0.1)`, never re-resolve, never rebuild), or
  (b) let the outer `except ... raise` kill the daemon thread outright.
  Either way `_is_recording` stayed `True`, `_system_recording_loop` in
  `src/audio_capture/core.py` kept polling an empty buffer, and nothing was
  surfaced to the UI. Evidence for the "call ended" trigger: the last system
  transcript at 21:41 is the meeting participants saying goodbye and moving to a
  WhatsApp group.
- Secondary finding (not fixed here): `src/main.py` configures logging with no
  file handler, so the crash only ever went to stderr and was unrecoverable
  after the fact.

This BU is the two fixes the user asked for ("fix 1 and 2" from the diagnosis):
a supervised capture loop and an external watchdog. It does not add file logging,
does not touch the microphone recorder's capture path beyond giving it the same
watchdog coverage, and does not change transcription, chunking, or the RAG
pipeline.

Tasks (all completed):

Fix 1 — supervised loopback capture (`src/audio_capture/system_recorder.py`):
- Rewrote `_recording_thread` as a supervisor loop that owns the lifetime of the
  capture, not a single stream. It exits only when the stop event is set; it
  never propagates an exception.
- New `_capture_once(stop_event)`: resolves the loopback mic (re-resolving
  `default_speaker()` every call, so a device change is picked up), opens the
  recorder context, and pumps ~1s frame reads. It returns cleanly — never raises —
  on any fault: `loopback_max_consecutive_errors` (default 5) consecutive
  `record()` exceptions, or no frames delivered for `loopback_silent_stall_seconds`
  (default 20s).
- After a fault the supervisor rebuilds with interruptible exponential backoff
  (`loopback_backoff_initial` → `loopback_backoff_max`, default 1s → 30s), reset
  to the floor after any capture that ran healthily for ≥30s so an isolated late
  fault does not inflate the delay.
- `_get_loopback_microphone` still raises `RuntimeError` on failure, now caught by
  the supervisor instead of killing the thread.
- Added health surface consumed by the watchdog: `seconds_since_last_data()`,
  `is_stream_active`, `is_thread_alive`, `restart_count`, `last_error`.
- `_data_buffer` reads/writes are now guarded by `_buffer_lock`.
- `stop()` join timeout raised to 5s and buffer return is lock-safe and
  idempotent.

Fix 2 — watchdog (`src/audio_capture/core.py`):
- `ChunkedAudioRecorder`: stamps `_last_chunk_time` on every saved chunk; records
  `_started_at`; new `is_thread_alive` property; new `check_health(stall_seconds)`
  returning `(healthy, reason)` with a post-start/restart grace window (so a slow
  device open does not trip the watchdog) — for the system source it also checks
  the underlying `SystemAudioRecorder` supervisor is alive and that
  `seconds_since_last_data()` is within `stall_seconds`.
- `ChunkedAudioRecorder.restart()`: signals the current loop to stop and joins it;
  refuses (returns `False`) if that thread is wedged, so a second loop is never
  started alongside a live one (no double-writing); for the system source builds
  a fresh `SystemAudioRecorder` (re-resolves the device) before restarting the
  loop in place, preserving `self.chunks` and all callbacks.
- `DualSourceChunkedRecorder`: new `on_status(source, message, is_error)`
  constructor arg and `_emit` helper; a watchdog thread started in `start()` /
  stopped in `stop()` that every `watchdog_interval_seconds` (15s) checks both
  recorders and calls `restart()` on an unhealthy one — rate-limited by
  `watchdog_restart_cooldown_seconds` (20s) and capped at `watchdog_max_restarts`
  (30), after which it emits a "giving up" status and stops trying. New
  `is_healthy` and `restart_count` properties. `create_dual_source_recorder`
  gained the matching `on_status` passthrough.

Wiring (`src/app/session_manager.py`):
- New `_on_audio_status(source, message, is_error)` that relabels the source
  ("System audio" / "Microphone") and routes the event through `_update_status`,
  so a lost/restored stream shows on the UI status bar.
- Both `dual_recorder_factory(...)` call sites (`create_session`, `load_session`)
  pass `on_status=self._on_audio_status`. Pause/resume re-arm the watchdog through
  the existing `stop_recording` / `start_recording` path.

Config (`src/config.py`):
- New `AUDIO_CAPTURE` dict holding every tunable above
  (`loopback_max_consecutive_errors`, `loopback_backoff_initial`,
  `loopback_backoff_max`, `loopback_silent_stall_seconds`, `watchdog_enabled`,
  `watchdog_interval_seconds`, `watchdog_system_stall_seconds`,
  `watchdog_max_restarts`, `watchdog_restart_cooldown_seconds`). Both modules read
  it defensively (fall back to literals if the import fails).

Tests added (`tests/test_system_recorder_resilience.py`, 8 tests, injects a fake
`soundcard` module plus stubs for `webrtcvad` / `sounddevice` which are not
installed in this environment):
- supervisor rebuilds the stream after a `record()` fault burst, keeps the thread
  alive, re-opens the stream context, and re-resolves `default_speaker()`;
- supervisor recovers when `default_speaker()` fails the first N times;
- supervisor rebuilds on a silent stall (empty frames);
- `stop()` returns promptly and the thread exits;
- `get_audio_data()` is `None` when not recording;
- watchdog restarts an unhealthy recorder and emits an error + a "restored"
  status event;
- watchdog leaves two healthy recorders untouched (no restarts, no events);
- watchdog stops retrying and emits "giving up" after `watchdog_max_restarts`.

Out of Scope:

- No change to transcription, VAD, chunking, or the RAG pipeline.
- No change to the microphone capture algorithm — it only gains watchdog coverage

- No device-change event subscription via the OS; recovery is fault-driven +

- No UI beyond routing status strings to the existing status bar.
