# BU094 — Session Router Coverage And Scoring Repair

Status:
Pending

Goal:
Fix Any Session retrieval so a question about a real, transcribed detail (a person's name, their role, an exact fact) reliably routes to the session that actually contains it, instead of silently answering "no information" or routing to an unrelated session. This BU is a diagnosis-driven repair of the BU089 Tier-1 router (`src/rag/router.py`) and its BU091 profile pipeline (`src/rag/indexer.py`, `src/rag/migration.py`) — not a rewrite and not a new retrieval architecture.

Context:
Reported symptom: asking "in what session does Miguel the records coordinator talk?" against a corpus where a session's transcript literally opens with "My name is Miguel and I am the graduate registration and records coordinator..." returns "no information in the transcripts" almost every time, for this and other queries. Diagnosed directly against a working copy of the production `chronicle.db` (never the live file) with `src/rag/router.route_sessions`, `src/rag/indexer.py`, and raw FTS queries. Three independent, verified root causes, all real and all needed to fully fix the symptom:

1. **Profile coverage gap.** `route_sessions` can only ever return a session that has a row in `session_profiles` (`db.get_session_profiles()`, loaded by `_load_cache` in `src/rag/router.py:88`). On the diagnosed database, `rag_documents`/`rag_chunks` existed for roughly half the sessions (content was indexed) but `session_profiles` existed for only two sessions total — including the "Miguel" session, which had full chunk data but no router profile at all. Tier-1 routing was therefore blind to nearly the whole corpus regardless of query wording. `index_session_content` (`src/rag/indexer.py:239`) calls `db.rebuild_rag_fts()` unguarded (no try/except) *before* the profile refresh step; any exception there — or any earlier interruption of a run — aborts the function and skips `index_session_profile` even though `_sync_document` already committed the session's chunks, producing exactly this "has chunks, no profile" asymmetry. Separately, the only user-facing recovery action, Settings → "Reindex All (RAG)...", hardcodes `backfill_corpus(force=True)` (`src/app/window.py:193`), which forces a full resync + re-embed + full-table FTS rebuild for *every* session on *every* run — expensive enough to be worth interrupting on a real corpus. Verified directly: `backfill_corpus(db, force=False)` filled in every missing profile for the whole corpus in under one second (no docs/chunks were unchanged-skipped so nothing expensive re-ran), because `index_session_profile` only skips when a profile already exists unchanged — a missing profile is never skipped, forced or not.
2. **Profile blind spot.** `build_session_profile` (`src/rag/indexer.py:379`) builds the router's only signal for a session from name + date + AI summary text — never the transcript. The diagnosed summary retained "Miguel" but not his exact title "records coordinator" (present only in the raw transcript); any FTS query for that phrase alone matches nothing in *any* session's profile.
3. **Scoring instability (the decisive cause).** Confirmed by direct repro *after* fully repairing coverage (task 1): `route_sessions` still never returns the correct session for the reported query. Two compounding issues: (a) `extract_keywords`'s stop-word set (`_PROFILE_STOP_WORDS`, `src/rag/indexer.py:344`) omits common auxiliary/modal verbs ("does", "did", "do", "have", "has", "had", "will", "would", "can", "could", "should"), so a query like "...does Miguel..." injects "does" as a real keyword; (b) the lexical half's score is a per-query `_min_max` over only the sessions that got *any* FTS hit (`route_sessions`, `src/rag/router.py:187`), with no floor tied to absolute match quality (unlike the cosine half's fixed `COSINE_FLOOR`/`COSINE_CEIL` rescale). A short, unrelated session whose profile happens to contain "does" — or an incidental homograph match, e.g. "records" as a verb ("...an app that *records* conversations...") scoring a higher raw BM25 rank than "records" the noun in the actually-relevant session — gets normalised to the top of the 0–1 range, while the session containing the one specific, correct, rare term ("Miguel") gets normalised toward 0 and dropped below `MIN_SCORE`. This reproduces with the full corpus profiled, so it is not a coverage artifact: it is a scoring bug in its own right, and the primary reason the reported query fails end to end.

See docs/build_plan/ANY_SESSION_REFACTOR.md (BU089 §on the router, BU091 on the profile/embedding pipeline) for the surrounding architecture. This BU does not touch BU090's answer contract, BU092's offer decision, or BU093's UI — it only makes the routing those depend on trustworthy.

Tasks:
- In `index_session_content`, wrap `db.rebuild_rag_fts()` in its own try/except (log and continue, mirroring the "best-effort" comment already on the profile-refresh block) so an FTS rebuild failure can never prevent the router profile from being stored for a session whose documents/chunks already synced successfully. Order or isolate the two steps so a failure in either is fully independent of the other.
- Change the Settings → "Reindex All (RAG)..." action (`src/app/window.py`) to run `backfill_corpus(force=False)` by default — verified to repair all missing profiles cheaply (no unchanged-content resync, no unnecessary re-embedding) — and keep a full forced rebuild available as an explicit secondary option (e.g. a confirmation checkbox or a separate menu entry) for the genuine "chunking scheme changed, rebuild everything" case. Do not remove the forced path; just stop making it the only one.
- Add common English auxiliary/modal verbs ("does", "did", "do", "have", "has", "had", "will", "would", "can", "could", "should") to `_PROFILE_STOP_WORDS` in `src/rag/indexer.py` so they never enter `extract_keywords` output for either profile text or query terms.
- Replace the lexical half's unbounded per-query `_min_max` normalisation in `route_sessions` with something that reflects absolute match quality rather than only relative rank among whatever happened to get a hit this query — e.g. rescale BM25 the way the cosine half already does (a fixed reference floor/ceiling tuned against real profile data), or weight by the fraction of extracted query terms a session's profile actually matched, or both. The concrete mechanism is an implementation choice; the required outcome is the test below.
- Extend `build_session_profile` to also draw on transcript content, not summary alone, so a term the summary paraphrases or drops (a title, a quoted phrase) is not permanently invisible to the router — e.g. mix `extract_keywords` output from the raw transcript into the profile's keyword/text signal, bounded so profiles stay compact (do not embed the full transcript). Keep the profile assembly a pure, bounded function; do not change the transcript chunking or Tier-2 context builder.
- Re-run `invalidate_profile_cache()` semantics stay correct after these changes (profile text/keyword changes must still bust the router's in-memory cache via the existing signature mechanism — no new caching bug).
