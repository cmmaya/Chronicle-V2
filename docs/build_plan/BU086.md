# BU086 — Fix RAG FTS MATCH Clause

Status:
Pending

Goal:
Make `search_rag_fts` actually filter and rank by the user's query so RAG retrieval returns relevant chunks instead of arbitrary ones.

Context:
`Database.search_rag_fts` (src/storage/database.py:1202) computes `fts_query = query.strip()` and never uses it. The generated SQL has no `WHERE rag_fts MATCH ?` clause, so every call returns the first N chunks by rowid with `bm25()` evaluating to `-0.0`. It does not raise, so `AssistantRetrievalTools.search_everything` treats the rows as valid and `AssistantAnswerService._get_all_sessions_context` never reaches its legacy fallback. This single defect is why both Any Session and Specific Session ignore the question. See docs/build_plan/ANY_SESSION_REFACTOR.md section 2.1.

Tasks:
- Add a `WHERE rag_fts MATCH ?` clause to the `search_rag_fts` SQL, combined with the existing `session_id` and `source_type` filters.
- Add a query sanitiser that makes arbitrary user text safe for the FTS5 grammar: strip or escape double quotes, drop bare FTS operators (`AND`, `OR`, `NOT`, `NEAR`, `*`, `^`, `:`, `-`) that would otherwise be parsed as syntax, tokenise into terms, and join the terms with `OR` so partial matches still rank.
- Quote each term to prevent FTS5 syntax errors from punctuation.
- Return an empty list when the sanitised query has no usable terms, rather than falling back to an unfiltered scan.
- Keep the existing `bm25(rag_fts) as rank` projection and `ORDER BY rank` (ascending; lower BM25 is more relevant).
- Preserve the current return-key contract: chunk_id, document_id, source_type, source_id, session_id, timestamp, title, content, rank.
- Keep the method read-only and fully parameterised.
