# BU129 — Machine-Readable Calendar Date In Due Dates Entries

Status:
Completed

Goal:
Make every Due Dates entry that the summary produces carry a calendar date the
app can parse, next to the date as it was spoken. "Send to Calendar" (BU133)
can then pre-fill a date and time without an extra LLM call.

Context:
- `templates.py` (the FULL / GENERAL_TRANSCRIPT prompts) asks for three fields
  per entry: `Title:`, `Due date:` (as spoken, plus the resolved date in
  parentheses when the recording date is known) and `Description:`. The
  resolved date is free text inside parentheses, e.g.
  `next week, Thursday or Friday (2026-09-24 or 2026-09-25)`. It cannot be
  parsed reliably.
- `generator.py` already passes `Recording date` in the context, so the model
  can resolve relative dates ("next Friday").
- `pixel_widgets.py` recognizes field lines with `_FIELD_LINE_RE` and renders
  them with `format_summary_body_html`. A new field that is not in that regex
  would render as plain body text that continues the previous field.
- Some entries have no single date: "at least 15 minutes prior (to each
  scheduled shift)" is recurring, and "Thursday or Friday" has two candidates.
  The template's existing rule "Never invent, estimate, or assume a date" still
  applies.
- Summaries created before this BU have no such field, so the parser must also
  handle them.

Decisions (agreed with the user):
- The date comes from a template field, not from an LLM call at click time.
- Field format, one line per entry, written after `Due date:`:
  - `Calendar date: YYYY-MM-DD`: all-day
  - `Calendar date: YYYY-MM-DD HH:MM`: timed, no end time stated
  - `Calendar date: YYYY-MM-DD HH:MM-HH:MM`: timed, with an end time
  - `Calendar date: none`: no recording date, recurring, conditional, two or
    more candidate dates, or unclear
- 24-hour clock, the local time of the recording. No time zone in the field.

Tasks:
- `templates.py`, Due Dates section:
  - Add the `Calendar date:` line to the per-entry format and document the
    four forms above.
  - Rules: resolve the date only from the Recording date in the Meeting
    Context. Use `none` when there is no recording date, and also for
    recurring, conditional, multi-candidate or unclear dates. Write a time only
    when one was stated. Never write a time for "end of day" or "morning".
  - Keep the existing `Due date:` line unchanged. It stays the version a person
    reads.
- New `src/calendar_sync/due_dates.py`:
  - `DueDateEntry` dataclass: `title`, `due_text`, `description`,
    `date: Optional[date]`, `start_time: Optional[time]`,
    `end_time: Optional[time]`, `index`, and a `fingerprint` property (see
    BU132).
  - `parse_due_date_entries(body: str) -> list[DueDateEntry]` splits the Due
    Dates section body into entries on each `Title:` line, as
    `format_summary_body_html` does. Hard-wrapped continuation lines join the
    field they follow.
  - `parse_calendar_date(value: str)` accepts the four forms and returns
    `(date, start, end)` or `(None, None, None)`. It rejects impossible dates,
    `end <= start`, and anything else.
  - Fallback for legacy entries with no `Calendar date:` line: if the `Due
    date:` text contains exactly one `YYYY-MM-DD`, use that date as all-day.
    Otherwise the date is `None`. Never guess from weekday names.
  - `No due dates were mentioned in the transcript.` yields `[]`.
- `pixel_widgets.py`:
  - Add `Calendar date` to `_FIELD_LINE_RE`.
  - `format_summary_body_html` skips the `Calendar date:` line. It is for the
    app, not the reader, and the human `Due date:` line already shows the
    date.
