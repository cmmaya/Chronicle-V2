# BU097 — Keyword Search For Transcripts And Conversations

Status:
Completed

Goal:
Give the user a real global "Search" dialog, opened from the sidebar **Search
Chats** button, with two modes:
- **Transcripts** — find transcript lines by keyword across every meeting
  session.
- **Conversations** — find past assistant chat threads whose title or any
  message contains the keyword(s).

Queries accept one or more space-separated keywords, AND-matched and
case-insensitive. Activating a transcript result jumps the transcripts panel to
that session; activating a conversation result loads it in the assistant panel.

Context:
- The sidebar **Search Chats** button is built at `src/app/window.py:2404`. Today
  its only behaviour is `self.search_chats_button.clicked.connect(lambda:
  self.session_search_input.setFocus())` — there is no content search anywhere in
  the app. `session_search_input` (`src/app/window.py:2593`) is a *session-name*
  autocomplete (`QLineEdit` + `QCompleter`, `_refresh_session_completer`), not a
  keyword search, and is unrelated to this feature.
- `db.search_transcripts(query, limit=10, session_id=None)`
  (`src/storage/database.py:1060`) already runs a **single-term** parameterized
  `text LIKE '%query%'` over `transcripts`, joined to `sessions` for
  `session_name`, `ORDER BY t.timestamp DESC LIMIT ?`. It does not split a
  multi-word query — `"foo bar"` only matches the literal substring `"foo bar"`.
  Callers today: `src/assistant/tools.py:238` and `src/assistant/service.py:579`
  (both pass a single natural-language string).
- There is **no** conversation/message content search. Schema:
  `assistant_conversations(id, session_id, title, created_at, updated_at)` and
  `assistant_messages(id, conversation_id, role, content, timestamp)`. Existing
  readers: `db.list_conversations()` (`src/storage/database.py:797`),
  `db.get_messages(conversation_id)` (`src/storage/database.py:901`).
- Loading a conversation into the assistant panel is `_on_conversation_selected(item)`
  (`src/app/window.py:524`): it reads `item.data(Qt.UserRole)` as the
  `conversation_id` and rebuilds the answer view from `db.get_messages`. Any new
  entry point should reuse this by id — extract a `_load_conversation(conv_id)`
  helper if `_on_conversation_selected` cannot be called directly with a
  synthesised item.
- Pattern to mirror for the dialog: `_on_past_conversations_clicked`
  (`src/app/window.py:5335`) — a plain `QDialog` + `QVBoxLayout` + `QListWidget`,
  `QMessageBox.warning` on DB failure.
- The RAG FTS index (`db.search_rag_fts`, `src/storage/database.py:1371`) is
  deliberately **not** used here: it is chunked, embedded and Any-Session-scoped.
  This feature is a plain literal keyword lookup over raw rows, consistent with
  the existing `search_transcripts` / `search_summaries` LIKE helpers.

Tasks:
1. `db.search_transcripts` — multi-keyword (`src/storage/database.py:1060`):
   - Split `query` on whitespace into terms. Whitespace-only / empty query →
     return `[]` (no DB hit).
   - Build one `t.text LIKE ? ESCAPE '\'` per term, combined with `AND`, plus the
     existing optional `t.session_id = ?` filter. Escape `\`, `%` and `_` inside
     each term so they match literally.
   - Unchanged: joined `session_name`, `ORDER BY t.timestamp DESC LIMIT ?`,
     return shape (`dict(row)` + `session_name`), parameterized-only.
   - Single-term callers (`assistant/tools.py`, `assistant/service.py`) keep
     working — one term collapses to one `LIKE`.
   - Update the docstring: AND semantics, wildcard escaping, empty-query no-op.
2. New `db.search_conversations(query, limit=20)` (`src/storage/database.py`):
   - Split into whitespace terms; empty → `[]`.
   - A conversation matches when **every** term appears somewhere in the union of
     its `title` and its messages' `content`. Implement per term as
     `c.title LIKE :t ESCAPE '\' OR EXISTS (SELECT 1 FROM assistant_messages m
     WHERE m.conversation_id = c.id AND m.content LIKE :t ESCAPE '\')`, all terms
     AND-ed.
   - Return a list of dicts: the `assistant_conversations` row fields plus
     `match_count` (count of that conversation's messages matching any term) and
     `snippet` (first matching message `content` trimmed to ~160 chars; fall back
     to `title` or `""`). `ORDER BY c.updated_at DESC LIMIT ?`.
   - Each conversation appears **once**, regardless of how many messages match.
   - Parameterized only. Docstring documents AND semantics + empty-query no-op.
3. Search dialog (`src/app/window.py`):
   - New `_open_search_dialog()`; rewire `self.search_chats_button.clicked` to it
     (drop the `session_search_input.setFocus()` lambda).
   - `QDialog` titled "Search", ~640×520: a `QLineEdit` (placeholder
     "Keywords…"), a `QTabWidget` (or two `QRadioButton`s) with **Transcripts**
     and **Conversations**, a "Search" `QPushButton`, and a results `QListWidget`.
   - Trigger search on Return in the line edit and on the button; re-run when the
     active tab changes and a query is present. (No live/debounced search — keep
     it simple.)
   - Transcripts rows: `f"{session_name}  ·  {HH:MM:SS}"` on line 1, matching
     `text` elided on line 2; `Qt.UserRole` = `(session_id, timestamp)`. Source:
     `db.search_transcripts(query, limit=50)`.
   - Conversations rows: title (or `Conversation #{id}`) + `updated_at` date on
     line 1, `snippet` on line 2; `Qt.UserRole` = `conversation_id`. Source:
     `db.search_conversations(query, limit=50)`.
   - Empty query → placeholder row "Type keywords and press Enter"; no results →
     "No matches." (both non-selectable).
4. Result activation (`src/app/window.py`):
   - `QListWidget.itemActivated` (double-click / Enter):
     - Transcript row → close the dialog, select that session in the transcripts
       panel via the existing session-selection path
       (`_on_session_completer_selected` / whatever `session_search_input`
       activation calls) and set scope to Specific Session for `session_id`. Pass
       the timestamp through only if that path already supports scroll-to-time;
       otherwise session selection alone is enough.
     - Conversation row → close the dialog, `_load_conversation(conv_id)`
       (extract from `_on_conversation_selected`), and select the matching row in
       `conversations_list` if it is present.
   - Every DB call in the dialog wrapped in `try/except` → `logger.error` +
     `QMessageBox.warning`; the dialog stays open, no partial state.
5. Leave `session_search_input`, `_session_completer` and
   `_refresh_session_completer` untouched apart from no longer being the target
   of the Search Chats button.

Validation Requirements:

Required:
- Sidebar **Search Chats** opens the Search dialog (not just a focus jump).
- Transcripts tab: one keyword returns every transcript line containing it across
  all sessions, newest first; two keywords return only lines containing **both**
  (any order); a keyword present in no transcript shows "No matches."
- Conversations tab: a keyword in a message body **or** in the conversation title
  returns that conversation exactly once (not once per matching message); two
  keywords AND-match across the title+messages union.
- Double-clicking a transcript result focuses that session's transcripts panel;
  double-clicking a conversation result loads it in the assistant panel.
- Empty / whitespace-only query never raises and shows the placeholder row.
- No regression to `session_search_input` autocomplete, the Past Conversations
  dialog, "Search Chats" for other lists, or `assistant/tools.py` /
  `assistant/service.py` transcript search.
- Injection-safe: a query such as `%' OR '1'='1` is treated as literal text
  (parameterized + `ESCAPE`), returns nothing.

Out of Scope:
- FTS / BM25 ranking, fuzzy or stemmed matching, embedding search — literal
  `LIKE` only.
- Searching summaries or screenshots from this dialog (`search_summaries` already
  exists; a later BU can add a tab).
- Highlighting the matched keyword inside the transcripts panel or chat bubbles.
- Regex, quoted-phrase, or field-scoped (`title:` / `role:`) query syntax.
- Jump-to-exact-message inside a loaded conversation (loading it is enough).
- Persisting or surfacing recent / saved searches.
- Any change to `session_search_input` behaviour beyond removing the Search Chats
  focus shortcut.
- `Ctrl+F` / in-pane incremental find with match stepping — that is a separate
  effort: **BU098** (active-pane focus model) + **BU099** (in-pane find bar).
  This BU is the cross-session/cross-conversation *discovery* dialog only.

  chain of `LIKE ? ESCAPE '\'`; new `search_conversations` uses per-term
  `title LIKE ? OR EXISTS(messages...)`. Both return `[]` for an empty term list

  `session_search_input`.
