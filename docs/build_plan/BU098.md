# BU098 — Active Pane Focus Model

Status:
Completed

Goal:
Make the three top-level regions of the main window — the **left** Chronicle
sidebar, the **center** assistant workspace, and the **right** transcripts panel
— behave as one mutually-exclusive set of "focusable panes". Clicking anywhere on
a pane's own background makes it the **active pane**; the active pane draws a
subtly brighter border (a light illumination, not a glow). Focus also follows the
keyboard: when a child widget inside a pane gains focus, that pane becomes
active.

This BU ships **only** the focus/highlight substrate and a queryable
`self._active_pane`. It does no searching — it is the prerequisite for BU099's
context-sensitive `Ctrl+F`.

Context:
- The three shells are created in `_build_main_layout`-style setup around
  `src/app/window.py:2358`:
  `self.left_shell = self._build_left_sidebar()`,
  `self.center_shell = self._build_center_workspace()`,
  `self.right_shell = self._build_transcripts_panel()`, then added to
  `central_layout` with stretch `0 / 1 / 0`.
- Each shell's outermost widget is a `PixelPanel` (`src/app/pixel_widgets.py:73`).
  `PixelPanel.paintEvent` draws a single pixel-cut border via
  `pixel_round_rect_path`: outer panels use `BORDER_BLUE` (`#254D9C`), inner ones
  `BORDER_BLUE_LIGHT` (`#3A67C7`), `pen_width = 2`, fill `NAVY` / `NAVY_INNER`.
  `PixelPanel` sets `WA_StyledBackground = False`, `autoFillBackground = False`,
  and has **no** mouse handling and no active/inactive concept today.
- `_build_center_workspace` / `_build_transcripts_panel` / `_build_left_sidebar`
  each `return panel` where `panel = PixelPanel()`; child widgets (lists, scroll
  areas, bubbles, buttons) are laid on top. A "background click" is a
  `mousePressEvent` that reaches the `PixelPanel` itself because no child
  consumed it (e.g. the padding around a `QListWidget`, the gap above the input
  bar).
- There is currently no `QShortcut` for `Ctrl+F` (only `Ctrl+Return` /
  `Ctrl+Enter` on `question_input`, `src/app/window.py:2713`).
- Detached windows (`_on_detach_assistant`, `_on_detach_transcription`) are
  separate top-level windows and are **out of scope** — panes are the three main
  shells only.

Tasks:
1. `PixelPanel` active state (`src/app/pixel_widgets.py`):
   - Add `self._active = False` in `__init__` and `set_active(self, value: bool)`
     that stores it and calls `self.update()` only on a real change.
   - Add a `clicked = Signal()` class attribute; override `mousePressEvent` to
     emit `clicked` on `Qt.LeftButton`, then call `super().mousePressEvent(event)`
     (do not accept/consume — children still work, and clicks that reach the
     panel are background clicks).
   - `paintEvent`: when `self._active`, draw the border with a brighter pen —
     new palette constant `BORDER_BLUE_ACTIVE = QColor("#4A78D8")` and
     `pen_width = 3`; fill and cut geometry unchanged. Inactive path is exactly
     as today (no visual change when nothing is active / for `inner` panels,
     which are never panes).
   - Keep it cheap: no timers, no animation.
2. `PaneFocusController` (`src/app/window.py`, small plain class — no Qt imports
   needed beyond what the module already has):
   - Holds `self.active: str | None` and the ordered pane names
     `("left", "center", "right")`.
   - `set_active(name) -> set[str]`: validates `name`, returns the set of pane
     names whose active-ness changed (`{old, new}` or empty if unchanged or
     invalid). Pure — no widget access.
   - This is the unit-testable core; `MainWindow` owns one and translates its
     result into `PixelPanel.set_active` calls.
3. Wire it in `MainWindow` (`src/app/window.py`):
   - After the three shells exist: `self._panes = {"left": self.left_shell,
     "center": self.center_shell, "right": self.right_shell}`,
     `self._pane_focus = PaneFocusController()`, and a `_set_active_pane(name)`
     method that calls `self._pane_focus.set_active(name)` and, for each changed
     pane, `self._panes[p].set_active(self._pane_focus.active == p)`. Expose
     `self._active_pane` as a read-through property (or plain attribute kept in
     sync) returning `self._pane_focus.active`.
   - Connect each shell's `clicked` signal → `lambda n=name:
     self._set_active_pane(n)`.
   - `QApplication.instance().focusChanged.connect(self._on_global_focus_changed)`;
     `_on_global_focus_changed(old, now)` walks `now.parent()` upward until it
     hits one of the three shells (or `None`) and, if found, calls
     `_set_active_pane` for it. Guard against `now is None`.
   - Default active pane at startup: `"center"` (call `_set_active_pane("center")`
     once the layout is built).
4. Keep everything else untouched — no restyle of inner panels, no change to
   list/scroll widgets, no new menu items.

Validation Requirements:

Required:
- Clicking the background of the left / center / right panel makes exactly that
  panel show the brighter active border; the previously-active panel returns to
  its normal border. Only one panel is ever active.
- Clicking a child widget (a list, the question box, a button) also activates
  that widget's panel (via `focusChanged`).
- `self._active_pane` reports `"left"` / `"center"` / `"right"` accordingly and
  is `"center"` on startup.
- Inner `PixelPanel`s (transcript viewport, candidate box, history panel) never
  show an active border and are visually unchanged.
- No regression: sidebar buttons, session list, transcript stream, assistant
  input, scope combos all still work; no stray clicks swallowed.

Tests Required:
- yes

Tests (`tests/test_bu098.py`, plain-Python, no Qt harness — same constraint as
BU093/BU095/BU096):
- `PaneFocusController.set_active("left")` from empty → returns `{"left"}`,
  `.active == "left"`.
- switching `"left"` → `"right"` returns `{"left", "right"}`.
- re-selecting the current pane returns `set()` (no-op, no redundant repaint).
- an invalid name returns `set()` and leaves `.active` unchanged.
- (if a pure `resolve_pane_for_widget(widget, shells)` walk helper is extracted)
  a fake parent chain resolves to the right pane name and an unparented widget
  resolves to `None`.

Out of Scope:
- Any search / find behaviour (BU099).
- Applying the active-pane concept to detached windows.
- Tab / arrow-key cycling between panes, or a "focus next pane" shortcut.
- Persisting the active pane across restarts.
- Restyling inner panels or adding hover states.
- Changing panel sizes, collapsibility, or the existing sidebar-collapse toggle.

Implementation Notes:
- `PixelPanel` gains `_active` + `set_active()` + `clicked` Signal +
  `mousePressEvent`; `paintEvent` branches the pen on `_active`. One new palette
  constant `BORDER_BLUE_ACTIVE`.
- `PaneFocusController` is the tested core; `MainWindow._set_active_pane` is the
  glue that pushes state into the `PixelPanel`s.
- `focusChanged` handler keeps keyboard focus and visual active-pane in sync so
  BU099's `Ctrl+F` reads the right pane whether the user clicked or tabbed there.
- No schema, no DB, no new files beyond the test.
