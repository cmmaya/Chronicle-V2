# BU092 — Scope Switch Offer Decision And Payload

Status:
Complete

Goal:
Decide, on the service side, when an Any Session answer should offer the user a direct switch to Specific Session for one concrete meeting, pick that single session, and carry it to the UI as a structured offer — so the app can ask "Would you like to change the scope to Specific for session: <name>, <date>?" instead of showing an undirected list of candidates.

Context:
BU090 already detects that Any Session could not reach transcript-level detail (`should_hand_off` src/assistant/response_contract.py:107, applied in `_finalize_answer` src/assistant/service.py:352) and surfaces the routed candidates on `AnswerResponse.candidate_sessions`. What it does with that is show a relabelled multi-session list picker (`_display_candidates` src/app/window.py:5008), which forces the user to read and choose even when the router is confident about exactly one meeting. This BU adds the missing decision: when the top routed session clearly dominates, emit a single-session `ScopeOffer` instead; when it does not, leave the BU090 list-picker path untouched. It also stops the app from re-asking about the same session on every turn of a conversation once the user has declined. This BU is logic and plumbing only — the in-chat prompt widget is BU093. See docs/build_plan/ANY_SESSION_REFACTOR.md sections 2.6, 3.3 and decision 9.

Tasks:
- Add `src/assistant/scope_offer.py` holding a `ScopeOffer` dataclass with fields `session_id`, `session_name`, `start_time`, and a pure `build_scope_offer(routed_sessions, intent, evidence, declined_session_ids) -> Optional[ScopeOffer]`.
- Return an offer only when all of these hold: the BU090 handoff condition is true (`should_hand_off(intent, evidence)`), there is at least one routed session, the top routed session is not in `declined_session_ids`, and the top session dominates the field.
- Define dominance as: the top session is the only candidate, or its `score` exceeds the second-best score by at least `SCOPE_OFFER_MARGIN`. Add `SCOPE_OFFER_MARGIN = 0.15` to src/config.py as a named constant so the threshold can be tuned without hunting through code.
- Return `None` — not a partial or placeholder offer — whenever dominance is not met, so the BU090 multi-session picker keeps handling the ambiguous case with no behaviour change.
- Reuse `should_hand_off` from src/assistant/response_contract.py rather than restating the condition, so the two paths can never drift apart.
- The function must be pure and total: no database access, no exceptions on malformed or partial routed-session dicts (a missing `score` is treated as 0.0, a missing `session_name` falls back to `Session <id>`).
- Extend `AnswerResponse` with an optional `scope_offer` field defaulting to `None`, so existing consumers and tests are unaffected.
- Populate `scope_offer` in `_finalize_answer` (src/assistant/service.py:352) for Any Session answers only; leave it `None` for every other scope.
- When an offer is emitted, still populate `candidate_sessions` as BU090 does — BU093 decides which of the two presentations to show, and the fallback must stay available.
- Track declined offers per conversation on the service: add `decline_scope_offer(conversation_id, session_id)` and suppress any later offer for that `(conversation_id, session_id)` pair. In-memory only — no schema change, no persistence.
- A `conversation_id` of `None` (a brand-new conversation) must not collide with declines recorded for real conversations.
- Never persist the offer, and never render it into the answer text. It travels on `AnswerResponse` and is written to the log only, exactly like `intent` and `evidence`.
